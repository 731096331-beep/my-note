# 一、实验目的

掌握 Wireshark 抓包软件的基础使用方法，学会网卡选择、捕获过滤器、显示过滤器配置、数据包查看与 TCP 流追踪操作。
观察 QQ 传输图片、文字消息时产生的 TCP、QUIC 数据包特征，区分 QQ 业务流量与 DNS、ICMP、系统后台心跳等无关报文。
捕获 QQ 通信数据包，尝试分析能否从网络载荷中提取 QQ 账号信息。
理解 QUIC 加密传输原理，掌握热点网络拓扑的流量转发逻辑，认识传输加密对网络通信隐私的保护机制。
**对比 4 种场景流量差异：电脑发文字→手机、手机发文字→电脑、电脑发图片→手机、手机发图片→电脑**，学会通过报文标志位、报文长度、时间戳、特征标识识别业务流量。

# 二、实验环境

硬件：Windows PC 计算机、智能手机
软件：Wireshark 抓包工具（配套 Npcap 驱动）、PC 版 QQ、手机 QQ 客户端
网络拓扑：电脑与手机接入同一 WiFi 局域网，电脑使用 Wireshark 监听本机无线网卡流量；QQ 通信采用服务器中转模型，消息与图片数据先上传腾讯服务器，再转发至接收端。

# 三、实验原理

Wireshark 是开源网络数据包捕获与分析工具，可以监听选定网卡上收发的网络报文，解析以太网、IP、TCP、UDP 等多层协议头部信息。
QQ 采用服务器中转通信模型：**无论电脑、手机互相发送文字消息或是图片，发送端都先将数据上传至腾讯服务器，服务器再推送数据给接收端**。手机与电脑客户端之间不会在局域网直接传输聊天报文。
新版 QQ 的文字消息、图片传输优先采用 QUIC 协议，QUIC 基于 UDP 承载，内置 TLS 加密。应用层数据在本机加密后再发送到网络，链路上只传输密文。若无本次会话密钥，仅捕获数据包无法解密载荷，一般情况下看不到明文聊天内容、图片二进制。
QQ 同时保留少量 TCP 链路以及遗留 HTTP 通信接口（httpconn），这类接口请求参数会在 URL 中明文携带 uin（QQ 账号），可以被抓包工具直接读取，但请求体内业务数据仍为二进制私有密文。
QQ 还会周期性发送心跳包（`Heartbeat.Alive`）维持客户端在线状态，属于保活报文，不承载聊天内容。
实验中存在多种干扰报文：DNS 报文用于域名解析；ICMP 为网络探测报文；Windows 系统遥测上报流量，需要根据报文特征、目的 IP 区分过滤。

# 四、实验内容与实验步骤

## 前期准备

电脑、手机连接同一个无线网络，保证网络连通。电脑、手机登录同一 QQ 账号，打开双方的聊天窗口。关闭电脑多余后台软件，减少无关流量干扰。

## Wireshark 网卡与捕获过滤器配置

打开 Wireshark，选中电脑当前连接 WiFi 的无线网卡。在捕获过滤器输入：
`udp || tcp`
该规则同时捕获 UDP（QUIC）和 TCP 流量，准备抓包。

## 触发通信

实验组 1：电脑 QQ → 手机 QQ 发送图片
操作顺序：先开启抓包，再使用电脑 QQ 发送图片到手机 QQ，否则数据包丢失。
点击 Wireshark 左上角鲨鱼图标，开始捕获数据包；在电脑 QQ 聊天窗口，向手机 QQ 发送一张图片；等待手机 QQ 完整接收图片，点击停止捕获，记录报文。

实验组 2：手机 QQ → 电脑 QQ 发送图片
操作顺序：清空上一轮抓包缓存，重新开启抓包；在手机 QQ 聊天窗口，向电脑端 QQ 发送图片；等待电脑 QQ 完整接收图片，停止抓包。

> 
> 注意：电脑上 Wireshark 抓包，抓取的是**电脑与腾讯服务器之间的下行流量**（服务器把图片下发给电脑）。手机上传图片到腾讯服务器的上行流量发生在手机网卡，电脑网卡无法捕获手机到腾讯服务器的上传报文。

实验组 3：电脑 QQ → 手机 QQ，发送文字消息
清空缓存，开启抓包；电脑 QQ 向手机 QQ 发送一段文字消息；等待手机收到消息后停止抓包，记录报文。本次抓包可观察到 UDP 承载的 QUIC 流量，报文内含有 `Heartbeat.Alive` QQ 心跳标识，载荷中携带 QQ 账号标识。

实验组 4：手机 QQ → 电脑 QQ，发送文字消息
清空缓存，开启抓包；手机 QQ 向电脑 QQ 发送一段文字消息；等待电脑收到消息后停止抓包，记录报文。本次抓到服务器下发的 TCP 流量，报文带有 `PSH,ACK` 标志位，代表推送业务数据，载荷中同样携带 QQ 账号标识。

## 筛选 QQ 流量

在 Wireshark 上方【显示过滤器】，结合腾讯服务器 IP 筛选 QQ 流量，观察抓包时间窗口内在发图、发文字瞬间产生的报文。
UDP 报文：对应 QUIC 加密流量；
TCP 报文：对应 QQ 消息推送、遗留 httpconn 接口通信流量。

## 分析数据包

筛选到目标报文，右键选择 Follow → TCP Stream / Follow UDP Stream，查看完整会话数据。

- TCP 流：可以在 HTTP 请求 URL 中观察到 uin 参数，提取 QQ 账号；`PSH,ACK` 标志表示服务端推送消息给本机。
- QUIC (UDP) 流：可观察到 `Heartbeat.Alive` 心跳标记，是 QQ 客户端保活特征。
请求与响应载荷为 QQ 私有二进制数据，无法直接还原图片与聊天明文。

## 区分无关干扰流量

DNS 报文：报文短小，用于域名解析腾讯服务器域名，不是聊天内容；
ICMP 报文：网络探测包，和 QQ 业务无关；
Windows 遥测、软件后台包：系统上报数据，通过目的 IP 可以区分排除；
QQ 心跳包：周期性极小数据包，仅用来保持在线，不是消息报文。

整理四组实验现象与数据，完成分析。

# 五、实验结果与分析

本次实验在同一局域网环境下，电脑使用 Wireshark 抓包，分别捕获**电脑 QQ 向手机 QQ 发送图片**、**手机 QQ 向电脑 QQ 发送图片**、**电脑 QQ 向手机 QQ 发送文字**、**手机 QQ 向电脑 QQ 发送文字**四种场景下的网络流量。
实验操作：设置捕获过滤器`udp || tcp`，分四次独立捕获流量。
抓包捕获到两类 QQ 流量：

1. UDP 承载的 QUIC 流量：属于新版 QQ 加密通信流量，可观察到 `Heartbeat.Alive` 心跳标识；载荷全部为加密二进制密文，无法直接提取明文聊天内容或图片原始数据。
2. TCP 协议流量：包含消息下行推送包与遗留 httpconn 接口 POST 请求。下行推送报文带有`PSH,ACK`标志，代表服务器向电脑推送消息；在 httpconn 请求 URL 参数中存在 uin=731096331，uin 即为 QQ 账号，成功提取账号信息。报文载荷内标记 PicUp.Echo，属于图片上传应答控制包，**仅出现在图片上传方向（电脑→手机场景）**，用来确认图片上传通信状态，不是图片完整文件本体。请求体和服务器返回内容为 QQ 私有二进制数据，无法直接解析图片内容。

四个传输场景流量特点对比：

1. 电脑 QQ 发图至手机 QQ：电脑作为上传端，产生 PicUp.Echo 上传校验 TCP 包；电脑将图片上传腾讯服务器，之后服务器下发通知消息到手机端。抓包可见上传控制报文，可抓到带 uin 参数的 httpconn 请求。

2. 手机 QQ 发图至电脑 QQ：手机作为上传端，图片上传腾讯服务器的上行流量在手机网卡，电脑 Wireshark**抓不到手机上传图片的报文**；电脑网卡捕获的是腾讯服务器向电脑下发图片数据的下行流量，下行流量以 QUIC 加密包为主，一般不会产生 PicUp.Echo 控制包，但是依然可以抓到携带 uin 账号的 httpconn 信令报文。
{% asset_img image-1.png 手机发图至电脑：抓包结果 %}
3. 电脑 QQ 发送文字消息到手机 QQ：电脑作为发送端，文字消息上传腾讯服务器，产生少量 QUIC 小包，流内带有 `Heartbeat.Alive` 标识；电脑网卡可以捕获本次上传对应的 QUIC 报文与 httpconn 信令包。文字消息数据量很小，报文数量少，没有 PicUp.Echo 图片控制包。载荷是 QUIC 密文，无法直接看到聊天文字。
{% asset_img image-2.png 电脑发文字至手机：抓包结果（一）QUIC 流，含 Heartbeat.Alive 与 QQ 账号标识 %}
4. 手机 QQ 发送文字消息到电脑 QQ：手机将文字消息上传腾讯服务器（该上行流量电脑抓不到）；电脑网卡捕获腾讯服务器下发到电脑的 TCP 下行加密报文，报文带有`PSH,ACK`推送标志，报文数量少，无 PicUp.Echo 包，载荷为加密数据，不能直接读取文字内容。
{% asset_img image-3.png 手机发文字至电脑：抓包结果（一）TCP 下行包，PSH+ACK 标志，携带 QQ 账号标识 %}

QQ 采用服务器中转架构，**无论传输的是文字消息还是图片，无论哪个方向发送**，数据都需要先上传腾讯服务器，再由服务器转发到接收端，不存在客户端之间局域网直传数据包的情况。
实验中混杂多种干扰流量：DNS 域名查询报文、ICMP 探测包、Windows 系统遥测上报包、QQ 心跳包。DNS 包体积很小；心跳包为周期性小包；微软遥测流量目的地址为微软服务器，可以通过 IP 地址和报文特征区分。

业务流量对比总结：
文字消息：数据量极小，通信产生**少量 QUIC 小包或者 TCP 推送包**，报文数量少，不存在 PicUp.Echo 控制包；电脑上行发文字的 QUIC 流可观察 `Heartbeat.Alive`，手机下发到电脑的文字报文带有`PSH,ACK`标志。
图片消息：文件体积大，数据被拆分为大量分片报文，短时间内爆发大批量数据包；图片上传方向会出现 PicUp.Echo 图片上传校验包。

实验小结：本次四组对照实验，成功捕获 QQ 双向文字、双向图片传输场景下，客户端与腾讯服务器之间的 TCP、QUIC 流量。在遗留 HTTP 接口流量的 URL 参数中成功提取明文 QQ 账号；而主流 QUIC 流量全程加密，单纯抓包嗅探无法获取明文聊天文字与图片数据。本实验验证现代传输加密对用户隐私的保护效果；同时掌握即时通讯软件服务器中转模型，客户端之间不会直接在局域网传递报文。

> 
> 重点现象总结：手机向电脑发送文字或图片时，电脑端 Wireshark 仅捕获服务器下发给电脑的下行加密流量，**无法捕获手机上传到腾讯服务器的原始上行数据包**。

# 六、思考题

1. 电脑 QQ 发送图片给手机 QQ，为什么数据包不直接发给手机，而要经过腾讯服务器中转？
答：QQ 属于 C/S 架构即时通讯软件。客户端上线后所有消息、图片统一提交腾讯服务器，由服务器负责消息转发。无论电脑和手机是否在同一局域网，都采用服务器中转，客户端之间不会建立直连通道，保障消息可靠投递、多端同步。
2. 抓到的 QUIC 包是什么协议？为什么大部分流量看不到明文聊天信息？
答：UDP 上层承载 QUIC 协议，QUIC 内置 TLS 加密，所有应用层聊天数据在发送前加密，网络链路上只传输密文。缺少本次会话密钥，无法解密得到明文聊天内容。本次抓到明文 uin 是 QQ 遗留 httpconn 接口的特殊情况。QUIC 流中出现的 `Heartbeat.Alive` 仅为心跳保活标记，不携带聊天明文。
3. 图片传输和文字消息的流量特征有什么区别？本次抓到的 PicUp.Echo 包作用是什么？
答：文字消息数据量小，传输时仅产生少量 QUIC 小包或者 TCP 推送包；电脑上行文字 QUIC 流带有`Heartbeat.Alive`标识，服务器下行推送文字的 TCP 报文带有`PSH,ACK`标志。图片体积大，会被拆分为大量分片报文，在短时间内出现大批量数据包。 PicUp.Echo 是图片上传应答控制报文，**仅在图片上传方向产生**，是客户端向腾讯服务器上传图片过程中的握手校验包，用来确认图片上传通信状态，并不携带完整图片文件。
4. 手机 QQ 给电脑 QQ 发送图片 / 文字消息，电脑上 Wireshark 为什么抓不到手机上传数据包？
答：手机上传文字或图片数据是手机网卡→腾讯服务器的上行流量，数据传输发生在手机的无线网卡。电脑上的 Wireshark 监听的是电脑网卡，只能捕获进出电脑本机的数据包，因此只能抓到腾讯服务器下发到电脑的下行流量，无法捕获手机到腾讯服务器的上传报文。
5. 对比 QQ 文字消息和图片传输的报文数量，简述差异。
答：文字消息数据量很小，传输时仅产生少量数据包；图片文件体积大，数据会被切分为大量分片报文，在短时间内产生连续、数量较多的数据包。图片上传场景会额外出现 PicUp.Echo 图片校验 TCP 包，文字消息场景不存在该报文。

# 七、实验心得

本次 Wireshark 抓包实验，我熟练掌握了 Wireshark 的基础操作，学会捕获过滤器、显示过滤器配置以及 TCP、UDP 流追踪的方法，加深对 TCP、UDP、QUIC 协议的理解。本次一共设置 4 组对照实验：电脑向手机发图片、手机向电脑发图片、电脑向手机发文字消息、手机向电脑发文字消息，对比四种场景下 QQ 双向通信的流量差异。

实验中观察到 QQ 两种通信流量：主流 QUIC 加密流量载荷为密文，带有`Heartbeat.Alive`心跳标记，无法直接窃取聊天信息；而遗留的 httpconn 接口会在 URL 中明文携带 QQ 账号，服务器下行推送文字的 TCP 报文带有`PSH,ACK`标志。这让我认识到即使在加密通讯软件中，老旧接口设计仍存在账号信息泄露的风险。

同时我理解了即时通讯软件的服务器中转模型，客户端之间不会在局域网直接传递报文。并且体会到抓包存在网卡监听边界限制：电脑上抓包，只能监听本机网卡，无法捕获手机网卡发出的网络数据包。文字消息和图片传输的报文数量、报文类型有明显区别，图片上传会产生 PicUp.Echo 控制包，文字消息没有。实验过程中也体会到真实网络环境存在大量无关干扰报文，需要结合报文时间、长度、标志位、特征标识、目的 IP 综合筛选、分析目标流量，不能盲目抓取报文。
